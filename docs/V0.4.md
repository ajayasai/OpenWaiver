# OpenWaiver 0.4 — receipt-gated release assurance

This release adds a separate, fail-closed release-contract workflow. It does not
change the legacy `release-gate` endpoint's semantics or silently migrate old
records. Use `openwaiver-release` or `/releases` for the new workflow.

## What a passing result means

Every check named in an **independently approved contract** has an explicitly
pinned run ID, project, stream, tool, revision, tool version, rule-deck digest and
configuration digest. Every selected run is covered by an authorized producer's
Ed25519-signed receipt binding its complete normalized record, design digest,
execution start/finish, invocation/output digests, exit status and unfiltered
completion claim. Both execution age and import age are bounded. The current
policy must exactly match the contract's policy digest. Existing independent
review, context, multiplicity, expiry and ambiguity checks remain in force.

A final budget limits total waived findings, category counts and minimum remaining
expiry days. Missing receipts, unapproved contracts, revoked/out-of-scope keys,
changed policy, contradictory review history, and exceeded budgets block release.
The browser explains those blockers without modifying any waiver or approval.

A complete contract is not automatically a complete chip verification plan. The
operator must include all required checks and the producer must collect the full,
unfiltered results. A signature authenticates a claim; it is not proof of physical
execution, source dependency completeness, correctness of a waiver, or foundry
acceptance. No proprietary adapter or commercial superiority is asserted.

## Three separate trust decisions

1. The producer signs execution metadata using its own protected private key.
2. An operator independently reviews the contract and approves its SHA-256 digest.
3. A release publisher freezes the selected inventory and signs its capsule with a
   **different key**. Producer and publisher key reuse is rejected.

Trust is a local JSON file. The HTTP endpoint reads only the server-configured
`OPENWAIVER_RELEASE_TRUST_FILE`; request bodies cannot provide trust or register
keys. It reloads the file for each evaluation, so revocations and contract removal
are effective on the next request. Keep it outside the public repository, writable
only by trusted administrators, and replace it atomically when updating it.

The file has this shape (placeholders are deliberately not valid signing material):

```json
{
  "schema_version": 1,
  "approved_contracts": ["<reviewed-contract-sha256>"],
  "producers": [{
    "public_key_pem": "<producer Ed25519 public key PEM>",
    "not_before": "2026-09-01T00:00:00Z",
    "not_after": "2026-10-01T00:00:00Z",
    "revoked": false,
    "scopes": [{"project": "chip", "stream": "lint", "tool": "verilator"}]
  }],
  "publishers": [{
    "public_key_pem": "<different publisher Ed25519 public key PEM>",
    "not_before": "2026-09-01T00:00:00Z",
    "not_after": "2026-10-01T00:00:00Z",
    "revoked": false,
    "projects": ["chip"]
  }]
}
```

Choose validity dates for the actual deployment. There are no wildcard grants.
Public keys and approved contract digests must arrive through an independently
trusted channel, not from the capsule under inspection. The same trust policy is
used by the CLI. Filesystem/CLI operators remain trusted, not sandboxed tenants.

## Workflow

Install Python 3.11+ and the application in a virtual environment:

```bash
python -m pip install -e '.[dev,physical]'
openwaiver-release --help
```

First import the complete unfiltered reports, supplying actual tool versions and
SHA-256 digests of the rule deck and semantic configuration. Never invent a digest
or mark a partial/filtered report complete. For the new contract, every required
check must have nonempty pinned provenance; the permissive legacy defaults are
not enough. Record the resulting run IDs.

Create a draft contract using explicit runs, not an automatic "newest passing run":

```bash
openwaiver-release template --db workspace/openwaiver.sqlite3 \
  --project chip --revision candidate-A --run-id RUN_LINT --run-id RUN_DRC \
  --design-sha256 DESIGN_SHA256 --max-waived 5 --output workspace/contract.json
```

`RUN_LINT`, `RUN_DRC` and `DESIGN_SHA256` are placeholders. The design digest should
identify an immutable, complete input manifest including semantic build inputs,
not just a Git branch name. Each producer is responsible for binding the same
actual design. Review and edit the proposed contract, including `budget`:

```json
{
  "max_waived_findings": 5,
  "max_by_category": {"lint": 4, "drc": 1, "cdc": 0},
  "minimum_remaining_days": 7
}
```

The default total allowance is zero. Category limits further constrain the total;
an omitted category is still subject to the overall cap. Count units are effective
waived findings, not lines in a waiver file. Aggregate markers remain non-waivable.
Revision-only waivers are bound to the exact release revision; the days threshold
applies to waivers with date expirations.

After review, independently provision the exact contract digest into
`approved_contracts`. Changing any contract input requires renewed approval of the
new digest. The template command outputs the draft digest and `authorized: false`.
For an edited contract, compute `openwaiver.identity.digest(ReleaseContract(...))`
over the validated model; it is not a raw JSON file byte hash.

A trusted collector records this metadata for each completed execution:

```json
{
  "design_sha256": "<digest of immutable design input manifest>",
  "invocation_sha256": "<digest of actual invocation specification>",
  "stdout_sha256": "<digest of actual stdout bytes>",
  "stderr_sha256": "<digest of actual stderr bytes>",
  "started_at": "<timezone-aware execution start>",
  "finished_at": "<timezone-aware execution finish, before import>",
  "exit_code": 0,
  "complete": true,
  "unfiltered": true
}
```

The `attest` command signs **supplied metadata**; it does not run an EDA tool or
infer completion. It automatically binds the metadata to the verified database
run and refuses caller overrides of that binding. Output digests are retained
claims; raw stdout/stderr are not automatically included in capsules. Preserve
raw reports separately for parser/tool investigations. Tools using nonzero exit
codes for ordinary completed checks need a carefully qualified collection policy;
this release requires zero for acceptance and must not be used to hide a crash.

```bash
openwaiver-release attest --db workspace/openwaiver.sqlite3 --run-id RUN_LINT \
  --metadata workspace/lint-execution.json --key producer.pem \
  --output workspace/lint-receipt.json

openwaiver-release gate --db workspace/openwaiver.sqlite3 \
  --contract workspace/contract.json --trust release-trust.json \
  --receipt workspace/lint-receipt.json --receipt workspace/drc-receipt.json
```

The existing attestation key-generation utility creates Ed25519 keys. Private-key
files must be owner-only on POSIX (`chmod 600`). Do not upload keys, credentials,
real chip reports, receipts or capsules to the public source repository. Output
files are create-only and mode 0600 where supported.

## Signed portable capsules

```bash
openwaiver-release seal --db workspace/openwaiver.sqlite3 \
  --contract workspace/contract.json --trust release-trust.json \
  --receipt workspace/lint-receipt.json --receipt workspace/drc-receipt.json \
  --key publisher.pem --output workspace/candidate-A.owrelease

# Independent offline verification and time-based replay of frozen evidence:
openwaiver-release verify --capsule workspace/candidate-A.owrelease \
  --contract independently-reviewed-contract.json --trust independent-trust.json

# Also reconcile against the current audited database before release use:
openwaiver-release verify --capsule workspace/candidate-A.owrelease \
  --contract independently-reviewed-contract.json --trust independent-trust.json \
  --db workspace/openwaiver.sqlite3
```

Capture reads runs, all waivers in the required scopes, policy and attachments in
one verified database transaction. Unrelated projects and global audit history
are not exported. The publisher attests completeness of that selected inventory;
the capsule is not an independent proof of the whole database's history.

Offline verification checks an externally authorized publisher, the separately
supplied approved contract, exact ZIP membership and member hashes, referenced
evidence, execution receipts and deterministic policy replay. The recorded engine
version must match. Unexpected paths, symlinks, duplicate members, missing evidence
and oversized inputs are rejected; nothing is extracted or executed from the ZIP.
Limits: 128 MiB compressed, 256 MiB expanded, 10,003 members. No WORM storage or
trusted timestamp service is provisioned.

**Historical validity is not current authorization.** The output distinguishes:

- `historical_gate_pass`: replay at the signed assessment timestamp.
- `frozen_state_gate_pass_now`: current time constraints applied to frozen records.
- `live_state_checked`, `live_state_matches`, `live_gate_pass`: current database
  reconciliation, only when explicitly requested.
- `release_usable_now`: `null` offline; with live reconciliation, true only when
  frozen/time checks pass and current inventory and gate still agree.

A withdrawn approval may be invisible offline. A valid signature is not an answer
to that question. Use live reconciliation or the live gate before current release
use. These checks are point-in-time: they cannot promise no later changes after
the transaction. Distributed authorization, independent storage and deployment
interlocks remain operator responsibilities. Revoking a key or removing a contract
from externally supplied current trust can invalidate an older capsule.

Exit codes: 0 for a passing gate/verification; 1 for a valid but blocked decision;
2 for malformed, unauthorized, missing or unverifiable inputs. Offline verification
exit 0 concerns frozen evidence only; inspect the explicit live-state fields.
`seal` refuses blocked releases by default. `--diagnostic` explicitly permits a
signed blocked record, which remains blocked on replay.

## Browser and API

Open `/releases` on the running authenticated application. Load contract JSON and
one receipt JSON file per run (or paste a receipt array). The server's trust policy
must be provisioned. The page shows contract binding, both tool results, execution
receipt status, risk counts and blockers. Editing inputs invalidates old results;
disconnecting clears credentials and displayed evidence. Nothing is written to
browser local/session storage. `POST /api/release-assurance/evaluate` uses the same
engine and project authorization. Neither UI nor HTTP API signs capsules or stores
private keys. Existing `/`, `/physical` and legacy endpoints remain available.

## Reproduction and native scope

```bash
python -m pytest --cov=openwaiver --cov-fail-under=90
python scripts/release_browser_smoke.py
python scripts/native_release_rehearsal.py
```

The last two require Chromium/Playwright and native Verilator plus KLayout,
respectively. The native rehearsal creates synthetic RTL and GDS, executes actual
Verilator lint and KLayout width checks, independently reviews their findings,
signs receipts with separate publisher authority, verifies a two-tool capsule,
and demonstrates that missing/aged receipts block release. It is a conformance
fixture, not a production benchmark or qualification of Calibre/IC Validator.
