# OpenWaiver 0.2: scoped review and independently verifiable evidence

This release improves the existing application. It does not establish superiority to every commercial verification product. The qualification boundary is explicit: source-level regression tests, constructed workloads, authenticated browser checks and the executable/fixture named in a successful native conformance report.

## What changed

**Candidate retrieval.** Source-line and spatial indices replace whole-rule scans. Explicit object IDs are still considered. Candidates are never approvals. A dense query exceeding the configured budget remains ambiguous; no closest-match shortcut hides alternatives. Sparse source candidates remain distinguishable even when thousands of unrelated occurrences use the same rule and hierarchy. Differential tests compare retrieval with exhaustive similarity evaluation.

**Project authorization.** Tokens carry exact project grants, optional timezone-aware expiration and revocation. Lists, details, lifecycle mutations, comparisons, run assessments, exports and evidence downloads enforce those grants. File-backed registries reload on each request. A malformed registry denies access rather than keeping a cached credential active. A role such as `admin` does not override a project's grant. Shared workspace policy administration requires an unrestricted administrator. The filtered audit view does not return another project's events. Full evidence bundles contain the complete workspace audit prefix and are therefore intentionally denied to project-scoped API tokens; use isolated workspaces for separate confidentiality domains.

**Git review plans.** YAML can describe multiple explicit proposal/amendment operations. Preview is read-only. Apply pins the audit head, actor, target identity, record versions and preview digest, checks every operation, then commits all or none in one transaction. Amendments clear prior approvals. Plans cannot inject approvals, evidence or approved status. Merging a Git change is not an engineering approval. The browser's **Review plans** page generates, previews and applies the same plans as the CLI/API.

**Dependency-derived staleness.** A build adapter supplies an explicit file dependency graph and maps every imported occurrence ID to its dependency roots. The local collector hashes actual files and recursively binds their contents and declared edges. Changed includes can invalidate dependent targets without invalidating unrelated targets. Settings (defines, ordered include arguments, corners, etc.) must be declared by the adapter. This does not infer RTL dependencies or establish graph completeness: an omitted input is still omitted evidence. The API cannot read server source directories.

**Offline Ed25519 signatures.** An independently supplied public key verifies artifact bytes and a purpose-specific subject. Signed ledger checkpoints bind a sequence and chain head; subsequent legitimate appends are allowed, but truncation/replacement before that checkpoint fails. A separately retained minimum sequence rejects older checkpoints. No signing private key is accepted by the web API. These are explicit OpenWaiver envelopes, not DSSE, Sigstore, a certificate authority, trusted timestamps, KMS or WORM storage.

**Independent bundle replay.** `verify-evidence` verifies internal hashes, audit sequence and links, frozen record digests, waiver membership, evidence attachment bytes, and the assessment under the captured policy. A self-consistent unsigned bundle is not authenticated. Supply a detached signature and an independently distributed public key for authenticity of the exact bytes. Replay incompatibility with a future engine is reported as such; it is not silently treated as success.

**Native export scope.** Verilator export refuses a rule/file/line control that would also hide an unapproved finding at that scope. Explicit acknowledgment of other lossy constraints is still mandatory. `scripts/native_verilator.py` actually invokes the installed executable, imports two diagnostics, exports one approved exception, and verifies the unapproved sibling remains. It also checks that changed source revision evidence does not inherit the ledger approval. The tool version and fixture scope are recorded. Do not reuse a derivative control file as a durable approval ledger.

## Upgrade and compatibility

Back up a stopped/checkpointed SQLite database and preserve an external audit head before upgrading. Existing Run, Waiver, Policy and Snapshot schemas, `ow1` fingerprints and recorded digests are unchanged. No approval migration is required. Candidate classification can improve on new assessments; frozen snapshots are not rewritten. `verify-evidence` may report a replay mismatch when an old frozen candidate assessment used behavior changed in the new engine. Verify such archives with their original engine version and detached signature rather than rewriting the snapshot.

Legacy tokens that omit `projects` retain workspace-wide access. Review those grants explicitly. New CLI token creation requires `--project NAME` (repeatable) or `--all-projects`. `projects: []` grants no projects; `projects: null` is workspace-wide. Names are exact, case-sensitive, and not wildcard patterns. There is still no SSO/OIDC, tenant-specific database isolation, per-project policy or hostile-local-user protection. CLI actor/role flags are trusted operator attribution, not authentication.

```bash
openwaiver auth-create --file workspace/auth.json --name alice \
  --auth-role contributor --project Orion \
  --expires-at 2026-12-01T00:00:00+00:00
```

To revoke a token, remove its record or set `revoked: true` in the protected registry. Use atomic file replacement. The next authenticated request observes the new registry. Keep the file private. Administrative registry edits and local filesystem operators remain trusted.

## Review plan example

Global CLI flags precede the subcommand. Replace the run/occurrence IDs with actual values. The web dashboard does not require these shell steps.

```bash
openwaiver --db workspace/chip.sqlite3 --actor alice plan-template RUN_ID \
  --violation OCCURRENCE_ID --reviewers bob \
  --rationale 'Reviewed engineering exception for this exact source revision.' \
  --valid-revision RTL_COMMIT --output proposed-plan.yaml
openwaiver --db workspace/chip.sqlite3 --actor alice plan-preview proposed-plan.yaml \
  --output preview.json
# Inspect the plan and preview. Copy preview_digest from preview.json.
openwaiver --db workspace/chip.sqlite3 --actor alice plan-apply proposed-plan.yaml \
  --expected-digest PREVIEW_DIGEST --output applied.json
```

Every result is a proposal. Evidence attachment, submission and independent approval still happen through the existing lifecycle. Outputs are create-only to avoid overwriting reviewed files. A changed workspace requires regeneration/review, not skipping the stale-state check.

An amendment operation has `action: amend`, `waiver_id`, `version`, `expected_content_digest`, and `changes`. Allowed fields are rationale, owner, reviewers, expiration, exact revision and tags. Plans are limited to 1,000 explicit operations in one project. See `tests/test_plans.py` for atomic failure, approval-reset and concurrent-apply cases.

## Dependency graph example

Create this file privately in the immutable source checkout; IDs must match the imported report's occurrence IDs. Paths are canonical, workspace-relative POSIX paths; symlink dependencies are rejected.

```yaml
schema_version: 1
scope: {project: Orion, stream: lint, tool: verilator}
revision: RTL_COMMIT
settings: {defines: 'SYNTHESIS=1', include_order: 'rtl/include;ip/include'}
nodes:
  rtl/top.sv: {dependencies: [rtl/include/config.svh]}
  rtl/include/config.svh: {}
targets:
  OCCURRENCE_ID: [rtl/top.sv]
```

```bash
openwaiver context-build dependency-spec.yaml --root . --output context-A.json
openwaiver --db workspace/chip.sqlite3 --actor alice import violations.json \
  --format json --project Orion --stream lint --tool verilator --revision RTL_COMMIT \
  --complete --checked lint --context-manifest context-A.json
openwaiver context-compare context-A.json context-B.json
```

The collector validates the graph before reading files, rejects cycles and missing references, and uses iterative hashing to support deep dependency chains. Input budgets are 64 MiB/file and 512 MiB total. Every imported occurrence needs a root mapping; this is intentionally not a partial-context success path. Tool/rule-deck/configuration provenance is still checked separately by the existing engine.

## Offline verification

```bash
openwaiver keygen --private-key signing.key --public-key trusted.pub
openwaiver sign-file candidate.zip --private-key signing.key \
  --subject Orion/candidate-A --output candidate.signature.json
openwaiver verify-evidence candidate.zip --signature candidate.signature.json \
  --public-key trusted.pub --subject Orion/candidate-A
openwaiver --db workspace/chip.sqlite3 checkpoint --private-key signing.key \
  --subject Orion/ledger --output ledger.checkpoint.json
openwaiver --db workspace/chip.sqlite3 verify-checkpoint \
  --signature ledger.checkpoint.json --public-key trusted.pub --subject Orion/ledger
```

Distribute the public key through a separately trusted channel. Never trust a public key delivered only by the artifact being verified. Keep signing keys outside repositories and evidence bundles. Default signature lifetime is 24 hours; use `--hours` deliberately (maximum 8,760). Verification checks the verifier's current time. Signed claims are not timestamps from an independent time authority. Retain checkpoints outside the mutable database; signatures cannot detect the loss of evidence that no verifier retained.

## Measured results and reproduction

Local Linux/Python 3.13 run: **283 tests passed; 90.76% line coverage**. The offline Chromium checks passed. The local runtime blocked live-browser navigation and did not have Verilator installed; those checks must pass in GitHub Actions before claiming them completed. The CI workflow runs Python 3.11/3.12/3.13, package builds, live and offline Chromium, and native Verilator. Consult the exact PR commit's checks and artifacts for the authoritative remote result.

The same synthetic repeated-rule workload, default candidate limit 256, same host and interpreter, three assessment runs per case:

| Engine and size | Median assessment | Intended unique review candidates | Changed findings auto-waived |
|---|---:|---:|---:|
| v0.1, 10,000 findings / 10,000 waivers | 9.138 s | 0; all exceeded the whole-bucket budget | 0 |
| v0.2, 10,000 / 10,000 | 0.355 s | 10,000 | 0 |
| v0.2, 100,000 / 100,000 | 4.409 s | 100,000 | 0 |

This is a **25.7x measured improvement over OpenWaiver v0.1 on this workload**, not a commercial comparison, throughput guarantee or statistical safety proof. Findings share a rule, hierarchy and source path but are spaced 300 lines apart; each moves one line. Dense groups can still remain ambiguous. The 100,000 case used approximately 1.06 GiB peak process RSS, including input construction and complete output materialization. Timings exclude parsing, database/audit traversal, network, browser and EDA execution. Raw observations and host metadata are in `docs/validation/v0.2/`.

