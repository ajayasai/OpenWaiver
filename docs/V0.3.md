# OpenWaiver 0.3 — physical evidence and federated access

This release adds actual GDS/OASIS neighborhood extraction, a separate physical
review workspace, and federated JWT access-token validation. It does not claim
universal superiority, foundry certification, or full enterprise SSO deployment.
The exact commit's CI is the authority for validation results.

## What changes for an engineer

A DRC marker can remain identical while a nearby polygon, hole, layer or instance
placement changes. A report fingerprint alone does not capture that change.
OpenWaiver now retains a physical manifest with the imported run. Its context
hash covers the marker and the full polygon representations selected by an
explicit layer/window recipe. A changed or missing context blocks reuse of a
previous approval. The evidence travels with snapshots and signed bundles.

Two digest roles are deliberately separate:

- The authoritative context is anchored to the marker, preserves orientation,
  polygon holes, cutline vertices, properties, duplicate shapes and relative
  offsets, and is checked during import and run deserialization.
- A read-only correspondence signature considers eight **common** orthogonal
  rotations/reflections of the entire neighborhood. It is not a grant of approval.
  Repeated patterns remain ambiguous; moving individual shapes independently
  cannot produce an equivalent context.

Explicit placement is part of the managed finding metadata and therefore its
identity. A moved/rotated instance cannot silently inherit an old approval even
when its neighborhood is congruent. A different layout-file digest alone does
not invalidate an unchanged local context: only the declared neighborhood and
recipe determine that context. Global/electrical dependencies outside the recipe
are not inferred.

## Install and extract from a real layout

Use Python 3.11–3.13 for the tested matrix:

```bash
python -m pip install -e '.[dev,physical]'
openwaiver-physical --help

openwaiver-physical extract \
  --layout candidate.gds --top TOP --layer 1/0 --layer 2/0 --halo-dbu 500 \
  --report drc.json --format json \
  --project chip --stream physical --tool klayout --revision candidate-A \
  --output candidate-A.physical.json

openwaiver-physical import \
  --report drc.json --format json --manifest candidate-A.physical.json \
  --project chip --stream physical --tool klayout --revision candidate-A \
  --db workspace/openwaiver.sqlite3 --actor engineer \
  --complete --checked-category drc --tool-version YOUR_ACTUAL_TOOL_VERSION
```

`--complete` is the operator's assertion about the **unfiltered EDA run**, not
something established by opening a layout file. Do not set it for partial,
filtered, failed or unfinished runs. The default is incomplete.

Report occurrence IDs must be unique, and each finding's `hierarchy` must name an
actual cell under the declared root. Marker geometry is in that cell's local
coordinates, with explicit `um`, `nm` or `dbu` units. Unit conversion must land
exactly on the native database grid; no rounding is allowed. The manifest binds
the exact report bytes as decoded UTF-8 text, project/tool/stream, revision,
recipe, and layout digest. A new report requires a new manifest.

An example finding in the existing JSON format:

```json
{"schema_version":1,"violations":[{"id":"width-1","category":"drc",
 "rule":"WIDTH.120","message":"Minimum width violation","hierarchy":"MACRO",
 "geometries":[{"kind":"edge","unit":"dbu","points":[[0,0],[0,400]]},
               {"kind":"edge","unit":"dbu","points":[[100,0],[100,400]]}]}]}
```

When a cell is instantiated more than once, extraction refuses to guess. Supply
`--placements selections.json`, with an occurrence-to-placement map:

```json
{"width-1":{"rotation":90,"mirror":false,"dx":1000,"dy":500}}
```

The selection must match exactly one *actual* placement. Coincident duplicate
instances are still ambiguous. Arrays are expanded with explicit budgets.
Native placement order is mirror about local x, rotate counterclockwise, then
translate. Only unit-scale 0/90/180/270-degree transformations are accepted.

GDS may represent holes using cutlines; OASIS/native polygons can retain hole
rings. The reader preserves the native polygon representation without reducing
it to a box or discarding cutline vertices. Equivalent alternate file encodings
may conservatively produce different context digests.

### Explicit coverage and resource limits

The recipe selects whole polygons whose bounding boxes touch the marker's
bounding box expanded by the halo, across the explicitly declared layers.
Layer order is irrelevant. Layer identity, halo, database unit, root and reader
version remain part of the recipe. No inference of relevant layers is made.
An absent declared layer is rejected, rather than treated as proof of empty
coverage. Paths/text in the selected region and nonorthogonal/magnified hierarchy
are rejected rather than approximated or silently dropped.

Limits: 256 MiB layout bytes; 100,000 expanded hierarchy instances; 10,000
findings; 10,000 shapes per finding; 250,000 retained vertices per manifest;
8,192 vertices per polygon. A limit failure emits no partial manifest. Large
production jobs must be deliberately partitioned without misrepresenting check
coverage. These bounds do not bound a compressed native parser's allocation:
run layout extraction in a CPU/memory-limited worker for untrusted input. The
polygon model validates representation and nonzero area, not full geometric
simplicity, hole containment, electrical connectivity, or DRC correctness.

The JSON manifest can also be passed as `physical_manifest` to `POST /api/runs`.
This endpoint never reads arbitrary server filesystem paths. Physical manifests
cannot be combined with another source-window/dependency manifest on the same
run; use an explicitly reviewed adapter instead of silently overwriting context.

## Physical review workspace

Start the existing authenticated application, then open `/physical` on its
local address. The main application remains available at `/`.

Connect with a project-authorized local token or provisioned access token.
Choose the before/after run and occurrence IDs. The page displays retained
polygons with even-odd hole rendering, marker geometry, independent layer
visibility, fit controls, placement and provenance. It can retrieve read-only
whole-neighborhood correspondences. No action on this page edits or approves a
waiver. Tokens stay in memory; disconnect clears the evidence view. The
original dashboard's separate proposal/rebind/review workflow remains required.

Read-only endpoints enforce project authorization on both run IDs:

```text
GET /api/runs/{run_id}/physical/{occurrence_id}
GET /api/physical/compare/{before_run_id}/{after_run_id}
```

The result exposes `approvals_granted: 0`. Candidate lists above the response
budget report truncation explicitly; they never turn into positive matches.

## Federated JWT access tokens

OpenWaiver can act as a resource server for an externally provisioned identity
provider. It does **not** implement interactive authorization-code/PKCE login,
identity-provider discovery, remote JWKS retrieval, or session cookies. Use the
provider's established login/client tooling to obtain an access token.

An operator creates a private JSON trust configuration outside the repository:

```json
{
  "issuer":"https://identity.example.test/realms/engineering",
  "audience":"openwaiver-api",
  "jwks":{"keys":[{"kty":"RSA","alg":"RS256","use":"sig",
                      "kid":"provider-key-id","n":"PUBLIC_RSA_MODULUS_BASE64URL",
                      "e":"AQAB"}]},
  "bindings":[{"subject":"provider-stable-subject-id","client_ids":["eda-client"],
    "principal":{"name":"engineer","role":"contributor","projects":["chip"]}}],
  "required_scopes":["openwaiver"],
  "max_lifetime_seconds":3600,
  "leeway_seconds":0,
  "revoked_jtis":[],"disabled_subjects":[],"issued_after":{}
}
```

The modulus above is a placeholder, not a working signing key. Install the
actual provider's public JWK through a trusted administrative process. Never
copy a private JWK into the configuration or commit identity mappings publicly.
Validate the issuer's exact spelling and audience with its administrator.

```bash
export OPENWAIVER_FEDERATION_FILE=/private/openwaiver/federation.json
export OPENWAIVER_DB=/private/openwaiver/workspace.sqlite3
python -m uvicorn openwaiver.api:create_app --factory --host 127.0.0.1 --port 8765
```

Do not expose this localhost HTTP service directly. A deployment needs a
properly configured TLS reverse proxy and `OPENWAIVER_ALLOWED_HOSTS`. Local
tokens can coexist by explicitly supplying `OPENWAIVER_AUTH_FILE`; they remain
a separate trusted administration boundary. The CLI/database filesystem remains
a trusted operator interface, not a remote-authentication boundary.

The verifier requires an RS256 signature under an installed public key, an
access-token `typ` of `at+jwt` (or `application/at+jwt`), exact issuer and a single
exact audience, integer `iat`/`exp`, nonempty `sub`/`jti`/`client_id`, accepted
client ID, scope, bounded lifetime and valid optional `nbf`. ID tokens, unsigned
or HMAC tokens, duplicate JSON keys, token-controlled `jku`/`jwk` headers, missing
claims, unassigned subjects and invalid project mappings are rejected. Roles,
email addresses and project lists supplied by a token do not create grants.

The trust file is reread for every request, with bounded parsing and a
content-keyed cache. Atomic replacement supports key rotation, revocation,
disabling a subject and minimum issue-time cutoffs. A malformed/unavailable
configuration blocks federated authentication; a syntactically JWT token does
not fall back to a local token with the same bytes. The provider must issue
compatible access tokens; live provider interoperability has not been certified.

## Migration and evidence trust

Back up the workspace before upgrading. Legacy runs without a physical manifest
serialize as before, preserving existing audit digests. Old v0.2 records remain
readable. Runs created with v0.3 physical evidence must not be opened by an older
application that cannot understand their schema extension. Do not downgrade a
mutated workspace. Older evidence is not retroactively declared layout-verified.

A retained manifest establishes what evidence was supplied and binds that data
to the run. It does not establish that the report is truthful or that a signed
adapter covered every relevant design dependency. Trusted build/CI provenance,
independent approvals and external key/checkpoint protection are still needed.
The existing signatures authenticate artifacts; they are not a foundry signoff.

## Competitive evidence and qualification

Siemens already documents hierarchy-invariant Calibre Auto-Waivers and dynamic
pattern/context-based waivers. Synopsys documents IC Validator waiver workflows.
This release should therefore be evaluated on cross-tool governance, retained
portable evidence, reproducibility and explicit failure handling—not on a claim
that physical context was invented here.

- Siemens Auto-Waivers: https://www.siemens.com/en-gb/products/ic/calibre-design/physical-verification/auto-waivers/
- Siemens dynamic context: https://resources.sw.siemens.com/sl-SI/technical-paper-dynamic-waiver-methodology-with-calibre-pattern-matching/
- Synopsys ICV VUE: https://video.synopsys.com/icvalidator/detail/video/5973786295001/01---waivers-using-ic-validator-vue
- KLayout recursive shape transforms: https://www.klayout.de/doc/code/class_RecursiveShapeIterator.html
- KLayout complex transforms: https://www.klayout.de/doc/code/class_ICplxTrans.html
- RFC 9068 access-token profile: https://www.rfc-editor.org/rfc/rfc9068
- PyJWT validation API: https://pyjwt.readthedocs.io/en/stable/api.html

Native qualification is limited to the installed KLayout version, synthetic
GDS/OASIS files, declared geometry/transform subset and actually executed width
check in CI. Existing Verilator qualification remains a separate job. There is
no qualified Calibre/ICV/Jasper adapter, full electrical topology engine, licensed
head-to-head performance benchmark, production availability guarantee, database
row-level tenant isolation, or deployed enterprise identity certification.
